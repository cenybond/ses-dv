# Сборка, staging и выпуск

Подготовлены статическая сборка и локальный staging-server. Удалённая площадка, production hosting и получатель заявок не выбраны. Действующий `ses-dv.ru`, DNS и Tilda не изменялись. Этот документ — инструкция для последующего согласованного выпуска, не разрешение на публикацию.

## Локальное окружение

Используются существующий Node (`>=22.18.0`) и зависимости из package-lock. Новые библиотеки не добавлялись. Если node_modules отсутствует, восстановление — `npm ci` после объяснения/согласования установки. Не обновлять зависимости одновременно с релизом.

```powershell
Set-Location 'C:\Users\arsbo\Documents\ses-dv'
npm run dev
```

Dev предназначен для разработки. Для HTTP-статусов, миграции и CSP используется staging ниже. Не запускать dev и staging на одном порту одновременно.

## Конфигурация

`.env.example` содержит безопасные значения. Если `.env` ещё нет:

```powershell
if (-not (Test-Path -LiteralPath '.env')) { Copy-Item -LiteralPath '.env.example' -Destination '.env' }
```

`.env` игнорируется Git. Секреты не помещать в `PUBLIC_*`: эти значения доступны браузеру. Astro читает public config при сборке, отдельный server — при старте. Default: staging, формы/аналитика выключены, ID Метрики отсутствует. Legal-флаги в коде также false; одного env для включения недостаточно.

## Проверки и локальный staging

```powershell
npm run verify
npm run staging:serve
```

`verify` выполняет typecheck, build, token/copy и негативные проверки, dist/links, браузер, tests форм/privacy, SEO и staging HTTP. Browser check использует существующий Edge/Chrome. Отсутствие браузера или запрещённый loopback фиксируется как ограничение, не как PASS. Не отключать OS/browser protection.

`staging:serve` слушает `http://127.0.0.1:4321` только на этой машине; другой порт — через `STAGING_PORT`. Он читает `dist`, применяет подготовленные 301/410/404, отправляет noindex/no-store/CSP и защитные заголовки. API здесь принудительно disabled независимо от env. Не выставлять вспомогательный сервер в интернет.

Адресные команды: `npm run check`, `build`, `check-copy`, `check-links`, `test-forms`, `test-privacy`, `check-seo`, `test-staging`. Проверки dist/links/browser/seo/staging требуют свежего `dist`; после изменения кода сначала build. Итоги относятся к проверенной сборке, не к будущему live-host.

## Удалённый staging после выбора площадки

1. Согласовать с владельцем hosting, бюджет и доступ, подходящие для будущей обработки данных.
2. Создать отдельное окружение с аутентификацией. Robots.txt не заменяет ограничение доступа.
3. Разместить только `dist`, оставив staging/noindex и формы/аналитику выключенными. Не публиковать `.git`, `.env`, sources, server, node_modules или репозиторий целиком.
4. Применить host-specific routes/headers. Проверить реальные 301/404/410, fallback 404, HTTPS, canonical, отсутствие аналитики и 503 API. Не возвращать 200 для отсутствующих страниц.
5. При необходимости запускать `npm run leads:serve` как отдельный управляемый Node-сервис, disabled по умолчанию. Настроить reverse proxy, body/time limits и доверенный IP; `npm run preview` этого не делает.
6. Проверить основные desktop/mobile шаблоны, сохранить commit/build/env-версию без секретов. URL staging внести в handoff после фактического размещения.

## Production

Нужны материалы и права на фото, актуальные контакты/реквизиты, решения по REVIEW URL, утверждённые юридические документы, инфраструктура обработки, выбранный transport с подтверждённой доставкой, ID/схема Метрики, QA и явное разрешение владельца. Перечень — [plan](plan.md), [legal-review](legal-review.md), [security](security.md).

После этого отдельный review меняет legal-флаги вместе с текстами и версиями согласий. Настраиваются production origin/mode и только необходимые feature flags. В новой сборке проверяются robots/sitemap/indexable, опубликованные страницы, отсутствие технических пометок и неподтверждённых фотослотов. Production CSP разрешает только включённые интеграции; локальная CSP намеренно не разрешает Метрику.

Перед переключением сохранить backup действующего сайта, предыдущий проверенный артефакт, DNS/redirect config, ответственного и критерии отката. Изменение hosting, DNS, отключение Tilda и настоящий приём заявок — только по отдельному разрешению. [Rollback](rollback.md).

После переключения: smoke главной/контактов/шаблонов, все 50 старых URL, 404, согласованный тест подтверждённой доставки, robots/noindex, отсутствие аналитики до согласия, отзыв согласия, mobile-клавиатура и технический мониторинг без payload заявок. Затем sitemap отправляется в Вебмастер по согласованному доступу.
