# SEO и миграция

Источник решений — [URL-MIGRATION](../URL-MIGRATION.md), источник полного старого реестра — [URL-INVENTORY](../URL-INVENTORY.md). Исследование повторно не проводилось.

## Реализовано

- `src/data/redirects.ts`: ровно 50 старых путей, причина и тип обработки каждой записи. Не содержит правил для произвольных внешних адресов.
- 6 KEEP, 27 MOVE, 5 MERGE, 1 REDIRECT, 7 REMOVE, 4 REVIEW.
- 301 ведут сразу к конечной релевантной странице, без цепочек и массового переноса на главную.
- Два предложенных 410: `/mtb`, `/gratitude`. Пять служебных адресов: 404, включая `/index.html`.
- REVIEW: `/sro-p`, `/sro-s`, `/news`, `/page55167833.html`; status=null, target=null. Никакого автоматического 410 или редиректа. На staging неизвестный адрес даёт 404; судьба production-адресов остаётся отдельным gate.
- `seo-head.astro`: title, description, self-canonical, OG, robots и Organization JSON-LD с известным названием, без вымышленных реквизитов/рейтингов.
- `robots.txt.ts`, `sitemap.xml.ts`: staging закрыт, sitemap пуст. После утверждения production sitemap строится из реализованных целей реестра. Нет REVIEW, новостей, документов, 404 и неутверждённых юридических страниц. Вымышленный lastmod не добавляется.

`PUBLIC_SITE_URL` — HTTPS origin без логина, пути, query/hash. По умолчанию https://ses-dv.ru, canonical staging указывает конечный домен; staging одновременно noindex. Production требует mode=production, env legal approval и явного одобрения юридического содержания в коде.

## Проверка

`node scripts/check-seo.mjs` после build проверяет 50 путей против исходного документа, существование целей, отсутствие цепочек, title/H1/description/OG/canonical всех страниц, закрытие черновиков и содержимое sitemap. Реальные HTTP-коды и Location проверяются на подготовленном staging-сервере и затем на выбранном хостинге, поскольку Astro build сам не применяет правила веб-сервера.

## Перед релизом

1. Зафиксировать резервную копию действующего Tilda-сайта и старого sitemap; DNS не менять до разрешения.
2. Утвердить REVIEW и 410, актуальность вакансий/контактов, тексты и фотографии.
3. Перенести реестр в правила выбранного хостинга; проверить без цепочек HTTP→HTTPS, www→основной host, регистр и слэши. Сначала конкретный legacy mapping, затем общая нормализация.
4. Проверить все 50 адресов по HTTP, отдельно неизвестный URL с реальным 404. Не включать fallback всех путей на index.html.
5. Снять staging access/noindex только на утверждённой production-сборке; проверить robots и canonical непосредственно в ответах.
6. Подтвердить права в [Яндекс Вебмастере](https://webmaster.yandex.ru/), указать sitemap, проверить страницы/редиректы и ошибки обхода; отправить изменённые важные адреса на переобход.
7. Отслеживать 404, индексацию и посещаемость после запуска. Данные поисковых кабинетов и фактическая индексация сейчас не доступны; успех миграции не заявляется.
