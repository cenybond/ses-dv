# План отката

Production в этой задаче не изменялся; откатывать действующий сайт не требуется. Hero V4 сохранён в базовом коммите `5d8bfe8`. Это точка истории разработки, не резервная копия действующего сайта.

## До переключения

- Назначить ответственного, связь с владельцем, окно наблюдения и критерии остановки.
- Сохранить проверенный backup текущей Tilda/hosting и способ возврата. Не отключать старую площадку до окончания согласованного наблюдения.
- Сохранить предыдущую сборку, commit SHA, manifest, версию redirects и env-имена без секретов. Secrets резервируются отдельно штатными средствами площадки.
- Зафиксировать DNS/TTL и настройки hosting. Любое изменение DNS — отдельная авторизованная операция.
- Проверить совместимость старой версии приложения с обработчиком, схемой согласий и provider store. Полученные обращения не должны пропасть при переключении.

## Когда откатывать

Критические недоступные страницы/массовые 5xx, неверные redirects/404→200, недостоверная доставка, сбор без требуемого согласия, утечка данных/секретов, сломанная основная mobile-навигация или случайный noindex в утверждённом production. Некритичная декоративная проблема может исправляться патчем после оценки владельца.

## После разрешения ответственного

1. При риске обработки выключить серверный приём (`LEADS_ENABLED=false`, рестарт сервиса). UI получит честный 503 и сохранит ввод на странице. При проблеме аналитики выключить public flag и пересобрать; при необходимости временно ограничить её host CSP. Public flags не изменяют уже собранную статику.
2. Вернуть предыдущий проверенный артефакт и host/redirect конфигурацию штатным deployment-механизмом. Не менять production-файлы вручную и не использовать `git reset --hard` как способ выпуска.
3. Если переключали домен, вернуть сохранённые настройки по согласованной процедуре, проверить обе площадки с учётом DNS-кэшей. Новую площадку сохранить для диагностики.
4. Проверить HTTP-коды, контакты, старые URL, robots и состояние форм. Сохранить технические журналы без payload; статус полученных заявок уточнить у получателя.
5. Зафиксировать время, commit/артефакт, причину, воздействие и дальнейшее исправление. Для инцидента ПДн применять утверждённый процесс, не придумывать сроки уведомления.

## Обращения и повторная доставка

В текущем disabled режиме заявок и дискового store нет. В будущем rollback статики не удаляет доставленные обращения и не означает их повторную отправку. Не воспроизводить очередь без проверки idempotency и статуса провайдера. In-memory cache теряется при рестарте; стабильный provider key помогает только если утверждённый transport/провайдер действительно его поддерживает.

## Исходный код

Исправления оформляются новым commit/revert после diff-review и проверок, без force push, уничтожения истории и удаления пользовательских файлов. Явно указать branch/артефакт повторного выпуска. После исправления повторить негативные тесты, общие проверки и staging smoke, затем получить новое разрешение production-переключения.
