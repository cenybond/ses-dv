# Управление содержанием

Сайт собирается из типизированных данных. CMS не подключена. Источники `docs/content/source/` неизменяемы; публикация новой информации требует подтверждения владельца.

## Где менять данные

| Содержание | Файлы |
|---|---|
| Услуги | `src/data/source/services.ts` |
| Проекты каталога | `src/data/source/projects.ts` |
| Содержимое 13 страниц проектов | `src/data/source/project-details.ts` |
| Общие дословные фрагменты | `src/data/source/content-texts.ts` |
| Родитель ТЛТ | `src/data/source/tlt.ts` |
| 12 страниц видов работ | `src/data/source/work-details.ts` |
| Вакансии | `src/data/source/vacancies.ts` |
| Компания, отделы, преимущества | `company.ts`, `advantages.ts` в том же каталоге |
| Контакты | `src/data/source/contacts.ts` |
| Подписи интерфейса | `src/data/ui.ts`: `ui`, `pageui` |

Компоненты отображают данные, не содержат новых фактов о компании. Названия, абзацы и опечатки старого сайта сохраняются дословно. Повторяющиеся фразы ссылаются на один объект `SourceText`; проверка покрытия допускает этот общий объект только при полном совпадении текста внутри соответствующей страницы.

## Редакционная правка

1. Сохранить исходную строку и её `src` без изменения.
2. В рабочем реестре согласования указать исходную строку, предложенный текст, причину, источник, дату и ответственного.
3. До решения статус — `proposed`; после письменного подтверждения — `approved` с датой и ссылкой на подтверждение.
4. Новый утверждённый материал сохранять отдельным снимком, не изменяя снимок старого сайта.
5. Обновить данные и проверки так, чтобы новая строка также имела машинную ссылку на источник. Выполнить `npm run check-copy`, `npm run test-check-copy`, `npm run check`, `npm run build`, `npm run check-links`.

Нельзя молча исправлять «коплексов», «приезжаейте» и повтор названия вида работ ТЛТ. Это отдельные предложения для редактора.

## Добавление проекта и фотографии

Запись проекта содержит постоянный ID, английский slug, исходное название и ссылку на снимок. Страница создаётся шаблоном `src/pages/projects/[slug].astro`. Для ТЛТ используется отдельная страница; виды работ создаёт `src/pages/projects/tlt/[slug].astro`.

Сначала получить подтверждение названия, состава работ, права на фотографии и согласие на публикацию. Добавить новый снимок источника и типизированные данные; обновить счётчик и ожидаемое количество в проверках. Сопоставление услуги и проекта показывается только при `clientApproved: true` после согласования. Текущие связи сохранены, но скрыты.

Галерея `project-gallery.astro` принимает `images` со `src`, описательным `alt`, `width`, `height`. До утверждения снимков отображается один честный фотослот. Стоковые фото нельзя выдавать за объект СЭС. Исходные изображения Tilda сохранены как ссылки в архиве, но не загружаются в сайт.

После добавления фотографий подключить утверждённые изображения к странице проекта, а выбранную обложку — к `ProjectCard`. Размеры галерей известны заранее; сжатие WebP/AVIF и визуальная проверка кадрирования обязательны. У компонента карточки есть `photoSrc`/`photoAlt`; при переходе от фотослотов к реальным обложкам добавить соответствующие `width`/`height`.

## Вакансии

Три исходных вакансии сохранены в двух группах. Все имеют `active: false`; страница прямо сообщает, что набор уточняется. Нельзя менять статус без подтверждения актуальности, условий и процесса отклика. Сейчас отклик и резюме не собираются. Контактное действие позволяет уточнить вакансии по существующему адресу почты.

## Новости и документы

Подготовлены типизированные реестры `news` и `documents` в `src/data/publications.ts`. По умолчанию оба пусты: фиктивных материалов нет. Шаблон `src/pages/[...publication].astro` создаёт `/news`, `/news/{slug}` и `/documents` только при наличии проверенных записей со статусом `approved`. Для `draft` страниц, ссылок и sitemap-записей нет. Карточки — `news-card.astro` и `document-card.astro`.

Порядок добавления:

1. Создать запись со статусом `draft`, английским slug, заголовком, датой и текстом. У новости обязательны краткое описание и абзацы; у документа — описание, даты действия и доступный текст.
2. Указать `source.reference` — ссылку на сохранённый источник или подтверждение; `approved_by` и `approved_on` — кто и когда согласовал факты. Согласование прав на текст хранится отдельно в `rights`: статус, правообладатель и подтверждение.
3. Файлы помещать в `public/media/news/` (WebP/AVIF/PNG/JPEG) или `public/media/documents/` (PDF). Путь в данных начинается с `/media/`. Внешние URL, traversal и активные HTML-файлы запрещены. Для каждого файла записать MIME, байты, SHA-256 и отдельное подтверждение прав; у изображения также alt и реальные размеры.
4. Проверить актуальность документа. Будущие даты публикации, ещё не действующие и истёкшие утверждённые документы блокируют сборку до решения редактора. Скан без доступного текстового содержания публиковать нельзя.
5. Только после согласования сменить статус на `approved`. Выполнить `node scripts/test-publications.mjs`, общий check/build, проверки ссылок/SEO и визуально проверить новый шаблон. Во время build сверяются реальное наличие файла, размер и SHA-256.

Экспорты `published_news`, `published_documents` и `published_routes` содержат только разрешённое к публикации. Навигация и sitemap используют этот список. Любой новый материал остаётся частью обычного release-процесса: статус записи не заменяет разрешение на production-релиз и проверку безопасности самого PDF.

## Проверка выпуска

Запускать полный `npm run verify` после согласованных изменений, проверять desktop и mobile, а для карточек — длинные названия. Перед публикацией обновить `content-register.md` и закрыть соответствующие пункты `pending-client-input.md`. Сборка staging не подтверждает юридическое согласование или актуальность контактов.
