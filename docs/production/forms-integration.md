# Формы и подключение доставки

Статус: инфраструктура реализована, реальный приём выключен. Получатель, hosting и обработка персональных данных не согласованы. Доставка в production не проверялась и не включалась.

## Архитектура

Astro собирает статические страницы. Единый `contact-form.astro` используется в содержательных страницах и `request-dialog.astro`. Клиентский `src/scripts/forms.ts` отправляет JSON на относительный `/api/leads`; адрес получателя не приходит из браузера.

`server/index.mjs` — небольшой Node HTTP-сервис на `127.0.0.1:4322`, без сторонних библиотек. Reverse proxy выбранного хостинга должен обслуживать `/api/leads` на том же origin, а остальные запросы — из `dist`. Такой подход сохраняет статику и не связывает весь сайт с будущим провайдером. Официальные [Astro endpoints](https://docs.astro.build/en/guides/endpoints/) и [on-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/) требуют adapter для исполняемых Astro server routes. Если будет выбран поддерживаемый Astro-хостинг, этот отдельный handler можно адаптировать, не меняя форму; сейчас adapter не устанавливался. [Node adapter](https://docs.astro.build/en/guides/integrations-guide/node/) статическому сайту сам по себе не нужен.

Компоненты: `contact-form`, `request-button`, `request-dialog`, `consent-checkbox`, `form-status`. Один `RequestDialog` и один импорт `forms.ts` размещены в общем layout. Без JavaScript кнопки ведут на контакты, отправка формы недоступна; телефон и e-mail работают обычными ссылками.

## Минимальные данные

- Имя — 1–80 символов.
- Телефон либо e-mail — одно поле; телефон 10–15 цифр, e-mail не длиннее 254 символов. Сейчас общий диалог использует contact-режим и метку callback для кнопки обратного звонка. Компонент также поддерживает отдельный callback-режим только с телефоном для последующего согласованного сценария.
- Текст задачи — необязательный, до 2000 символов; вложений нет.
- Контекст из серверного реестра: `general`, `home`, `callback`, `contacts`, `about`, `service:s-01`…`service:s-10`, `project:prj-01`…`project:prj-14`, `work:prj-14-01`…`work:prj-14-12`.
- Отдельный, заранее не отмеченный checkbox согласия и версия утверждённого документа.
- Пустое поле-ловушка `website`.

Контексты — только метки. Они не задают получателя, transport, routing, уровень доступа или произвольный URL. Новые контексты добавляются в `server/lead-contract.mjs` и проходят тест.

## Выключенное состояние

Поля и отправка недоступны, рядом объяснение и прямые контакты. Клиент не читает и не сохраняет значения, не отправляет JSON. Нет localStorage/sessionStorage черновиков и никаких cookie формы. Сам endpoint возвращает `503 unavailable` до чтения тела. Он не хранит и не журналирует обращения. Пользователю не показывается сообщение об отправке.

Включение защищено двумя видами условий:

1. Проверяемые в Git флаги `legal_content_approved` в `src/data/site-config.ts` и `server/release-config.mjs`. Сейчас оба `false`. Менять только после реального юридического согласования и разрешения владельца.
2. Env-флаги и серверный transport. Случайного выставления одного env недостаточно.

## Transport contract

Интерфейс описан JSDoc в `server/transports.mjs`. `configure_transport()` пока возвращает только `disabled_transport`. В production нет тестовой реализации. Попытка запуска с включённым приёмом и отсутствующими согласованиями/транспортом завершает startup ошибкой.

Утверждённый transport реализует:

```js
// Серверный код; секреты никогда не импортируются в src/.
const transport = {
  kind: 'delivery',
  async send(lead, { signal, idempotency_key }) {
    // Здесь — вызов согласованного провайдера с timeout, escaping и idempotency.
    // Возвращать acknowledged: true только по подтверждённому ответу доставки.
    return { acknowledged: true, reference: 'подтверждение-провайдера' };
  },
};
```

Этот фрагмент объясняет интерфейс, не является готовым transport. Нельзя оставлять фиксированный `reference` в реальной реализации. Email, Telegram, CRM и webhook — возможные варианты после решения владельца, ни один не выбран. Запись в лог, фиктивный успех, `setTimeout` или постановка в необработанную очередь не подтверждают доставку.

`send` должен соблюдать `AbortSignal`, передавать стабильный idempotency key провайдеру и не передавать введённые строки в HTML, SMTP-заголовки, shell, SQL или URL без подходящей безопасной обработки. Секреты получает только серверный модуль из environment. Подтверждение провайдера не возвращается посетителю: handler создаёт непрозрачный receipt после ack.

## Переменные

| Переменная | Назначение |
|---|---|
| `PUBLIC_FORMS_ENABLED=false` | Сборка активного UI после согласования |
| `PUBLIC_LEGAL_APPROVED=false` | Публичный release gate |
| `PUBLIC_CONSENT_VERSION=` | Версия конкретного утверждённого согласия |
| `LEADS_ENABLED=false` | Серверный приём |
| `LEADS_LEGAL_APPROVED=false` | Серверный release gate |
| `LEADS_CONSENT_VERSION=` | Та же версия, что в форме |
| `LEADS_ORIGIN=` | Точный origin без завершающего `/`, только HTTPS в production |
| `LEADS_PORT=4322` | Loopback-порт отдельного сервиса |
| `LEADS_ENV=production` | `development` допускает HTTP только на localhost |
| `LEADS_TRUSTED_PROXY_IPS=` | Явные IP доверенного proxy, пусто по умолчанию |

Пример без секретов — `.env.example`. В env нет установленного получателя или универсального секрета; нужные имена добавляются вместе с утверждённым transport. `.env` не коммитить. Изменение `PUBLIC_*` требует пересборки статики.

## Локальная проверка и staging

```powershell
node --test --test-timeout=30000 scripts/test-forms.mjs
node --env-file-if-exists=.env server/index.mjs
```

Вторая команда по умолчанию запускает только выключенный endpoint. Не включает сбор данных. Для проверки в Windows среда может требовать разрешения loopback-соединений. Автотесты запускают временный server и синтетический transport внутри процесса; внешних запросов нет. Не тестировать на телефонах, адресах или сообщениях реальных людей.

На staging разместить статическую сборку и при необходимости выключенный handler за аутентификацией. Для `/api/leads` настроить: POST, body limit 8 KiB, read timeout, no-store и отсутствие body logging. Реальный transport, production счётчик и обработку ПДн на staging не включать.

Если используется reverse proxy, он должен перезаписывать `X-Real-IP` адресом своего клиента. Только после этого его точный socket IP добавляется в `LEADS_TRUSTED_PROXY_IPS`; иначе пользовательский header игнорируется. Без этой настройки несколько клиентов за proxy разделяют один rate-limit bucket — это безопасно, но непригодно для полноценного запуска.

## Отказы и повторные отправки

Клиент сохраняет ввод на странице при ошибке, не в browser storage. Успех и цель `lead_success` возможны только при HTTP 200 + `ok:true` + `code:delivered` + receipt. Текст и контакты в аналитику не попадают. При отказе пользователь получает понятное сообщение; ошибка инфраструктуры не отражается stack trace.

На стороне сервера: 5 попыток за 60 секунд на ключ клиента, 10 минут защиты от повторов. UUID ключа от браузера привязывается к хешу содержания и клиенту. Повтор подтверждённой заявки с тем же ключом возвращает тот же receipt без новой доставки. Другой текст с тем же ключом отвергается. Неопределённый исход/timeout сохраняется как `uncertain`: автоматического повтора нет, пользователю предлагается проверить получение напрямую.

Гарантия ограничена одним процессом и TTL. Состояние исчезает при рестарте; между инстансами не синхронизируется. До масштабирования необходимы общий idempotency/rate store, согласованный срок хранения и idempotency самого провайдера. Тексты заявок в cache не хранятся; там ограниченное число HMAC-ключей и статусов. HMAC-ключ создаётся в памяти процесса, IP не журналируется.

## Что требуется перед запуском

Выбор владельцем получателя и hosting; сведения об операторе и процессах; утверждённые юридические тексты и версия согласия; отдельное разрешение обработки; production HTTPS; транспорт с подтверждением доставки и idempotency; согласованный режим журналов, доступа и сроков хранения у провайдера; проверка ошибки/timeout/delivery на тестовых данных в выбранной инфраструктуре. После этого — отдельный code review release flags, пересборка и разрешение production-релиза.
